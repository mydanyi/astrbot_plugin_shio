# 星汐故障排查

先确认问题发生在 AstrBot、Shio、聊天模型、平台适配器还是其它插件。Shio 是官方事件链上的插件，后台出现错误不代表错误一定由 Shio 产生。

## 完全没有回复

0.5.1 修正了一个已复现问题：QQ 最终回复在 Agent 结束之后才装饰，旧代码先清掉最终标记，又把正确回复当作草稿拦下。网页原生流式输出走另一种顺序，所以“网页能回”不能证明 QQ 链正常。相关验证见 `tests/integration/qq_delivery.py`。

按顺序检查：

1. AstrBot 是否为 `4.27.4`，Shio 是否成功加载并启用。
2. 当前 QQ 号或群号是否在 Shio 允许范围内，是否同时进入禁用名单。
3. 这条消息属于 @、Reply-to-self、官方唤醒、名称直呼还是未点名聊天。
4. 未点名聊天是否开启“允许自然参与”，当前群是否在自然参与群号中。
5. 名称判断或自然参与模型是否可用，是否因总等待时间耗尽而保持安静。
6. AstrBot 当前聊天模型和 fallback 是否能正常回答普通消息。
7. 同一会话是否还有等待中的连续消息窗口。

Master 能绕过普通入口名单，但 Master 在群里的普通未点名发言仍属于自然参与，不会自动变成必回。

## 停用 Shio 后仍复读

停用插件只停止新的 Hook，不会删除已经写入 AstrBot conversation 的内容。旧 0.5 可能把官方群聊历史和异常工具调用结果带入长期会话；0.5.1 停止这条写入路径，但不自动清除旧数据，因此停用后仍可能继续复读。

处理原则：

- 不要把“插件已停用”当成“历史已恢复”。
- 不要直接删除 AstrBot 数据库或整个会话目录。
- 先备份受影响 conversation，再比较正常会话和异常会话的消息结构。
- 代码修复与已污染数据处理是两个独立动作。

对修复候选先使用专用测试 conversation；不要用“全库删除含某个关键词的消息”来清理生产数据。

## 回复很慢

一次回复可能包含多个等待：

- 连续消息安静窗口，默认 3 秒；
- 智能名称判断；
- 自然参与判断；
- 正式聊天模型和工具；
- 发送前审核及修改；
- 模型分段；
- 气泡间隔。

先临时使用以下组合定位：

- 名称唤醒改为“直接识别”；
- 关闭自然参与；
- 关闭发送前检查；
- 文本布局改为“合并为一段”；
- 气泡等待设为 0。

如果这样仍慢，优先检查 AstrBot 正式模型和工具链。辅助模型的“等待秒数”是当前模型和所有备用模型共享的总时间。

## 模型下拉列表为空

Shio 的名称判断、自然参与、审核和模型分段都应使用 AstrBot 的模型选择器。

1. 先在 AstrBot 中确认 Provider 已创建并成功加载。
2. 重载 Shio 或重启 AstrBot，让设置页重新读取模型列表。
3. 刷新浏览器设置页。

不要手写内部 Provider ID 来绕过空列表；这通常只会把加载问题隐藏起来。

## 气泡数量不对

如果 Shio 最多设置为 3 段，但实际收到更多文字消息，首先检查 AstrBot 内置分段是否同时开启。Shio 与 AstrBot 都分段时，同一文本可能被二次拆分。

Meme Manager 5.0.0 会合并相邻文本组件。0.5.1 将 Shio 布局移到 Meme 清理之后，避免文本刚分好又被合成一整段。

建议：

- 由 Shio 控制气泡时，关闭 AstrBot 内置分段；
- 先使用“按句分段”验证；
- 确认 Meme 图片不计入文字段数；
- 查看 Shio 是否因 TTS、文本转图片或 QQ forward 降级为官方单链。

Shio 的“最多文本段数”是上限，不保证每次都达到这个数量。无法安全分段时会保留完整单段。

## 没有表情包

Shio 不负责决定是否发表情包。即使没有启用 Shio 的任何辅助情感判断，Meme Manager 仍可以根据自己的设置和最终文本选图。

检查：

1. Meme Manager 是否已加载和启用。
2. 它自己的语义/情感选图配置是否可用。
3. 多文本组件时是否使用了适合的分开发送设置。
4. Shio 后续气泡是否取消、过期或发送失败；这种情况下会阻止后面的 Meme Hook 单独发图。
5. 最终审核是否清空或替换了文本。

不要通过在正文中输出 `&&meme:...&&` 来模拟图片发送；这表示 Hook 没有正确消费标记或链路顺序异常。

## 回复重复或一次出现多个近似答案

可能原因包括：

- AstrBot 内置分段与 Shio 分段同时开启；
- 同一事件被旧插件实例和新实例共同处理；
- 连续消息没有由同一个批次 owner 收拢；
- conversation 已保存重复正文或异常工具调用结果；
- Provider 自己返回了重复文本。

需要同时收集收到消息到最后发送完成的完整时间段日志，并核对：

- 同一平台消息 ID 启动了几次正式请求；
- 是否出现插件重载；
- 每个回复属于哪个真实事件；
- AstrBot conversation 中是否已经存在重复内容。

## Master 通知没有私聊、错误仍出现在群里

Master 通知不是“把所有 AstrBot 日志自动转发给主人”。它对配置允许的最终回复失败或审核失败首次提交固定脱敏摘要，同类故障限时去重。已开始的自然回复失败也适用；自然参与决定保持安静不算故障。

检查：

- AstrBot 是否正确识别 Master；
- 开启通知后 Master 是否与机器人进行过真实私聊以保存地址，且仍在官方管理员名单内；
- “启用 Master 通知”及对应失败类型是否开启；
- 是否处于同类故障去重期；
- 当前是否在勿扰时段；
- AstrBot 平台是否支持主动消息接口。

“已提交”不等于 QQ 已送达。Shio 不会重试，也不会把完整群聊正文写入告警。

日志中 `Shio review result=... elapsed_ms=...` 区分 `keep`（通过）、`repaired`（改写后通过）、`invalid`（格式错误）、`unavailable`（无可用审核结果）、`timeout`（预算耗尽）和 `rejected`（仍需修改但无法继续）。`Shio alert` 会记录待通知、去重、提交或发送失败；通知接口最多等待 8 秒，超时不阻塞后续对话，也不改为群发错误。

## QQ 图片下载 HTTP 400

类似下面的日志来自 AstrBot 媒体预处理阶段：

```text
Failed to download file from https URL host='multimedia.nt.qq.com.cn'
HTTP status code: 400
```

这表示 AstrBot 在调用 Shio 的聊天处理前下载 QQ 媒体失败。常见排查方向是临时链接已经失效、QQ 侧参数不再可用、适配器传入的 URL 不完整，或请求发生得太晚。

Shio 不负责下载这个 URL，也不能在插件内部伪造图片内容。排查时需要保留对应消息的时间、消息类型和 AstrBot/NapCat 适配日志，但不要公开真实下载链接。

## 群聊图片没有进入上下文

当前 0.5 的群聊上下文接入仍待修复。AstrBot 的“群聊消息记录注入上下文”可以配合图片转述模型处理媒体，而 Shio 当前错误地绕到了持久化消息历史读取。

在修复前，不要通过复制图片 URL、媒体占位符或持久化历史到 `req.contexts` 的方式补洞。

## 反馈问题时请提供

- AstrBot 版本、Shio 版本和平台适配器；
- 相关插件名称和版本，例如 Meme Manager、LivingMemory；
- 当前聊天模型及是否启用 fallback，不要提供密钥；
- 相关设置截图，遮住 QQ 号、群号和 Provider 凭据；
- 复现步骤、期望结果和实际结果；
- 从收到消息前几秒到最后发送或报错后的完整脱敏日志；
- 是否发生插件重载、容器重启或配置保存；
- 是否为新 conversation，还是复用了可能已污染的旧会话。

不要提交：

- API Key、Cookie、Token；
- 未脱敏的 QQ 号、群号和私聊正文；
- QQ 临时媒体下载完整 URL；
- 整个生产数据库。

## 安全的定位顺序

1. 先只读确认版本、插件状态和配置。
2. 使用新测试会话复现。
3. 关闭可选辅助环节，定位发生在哪一段。
4. 查看真实 AstrBot Pipeline 日志，不只看 Shio 自己的输出。
5. 在 Docker 测试环境复现后再修改代码。
6. 代码验证与生产数据清理分别取得确认。
