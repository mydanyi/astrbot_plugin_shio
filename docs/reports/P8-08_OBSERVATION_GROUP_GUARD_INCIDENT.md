# P8-08-OBS 旧群聊守卫误杀事故报告

## 结论

`2026-08-17T15:04:43Z` 至 `15:04:57Z` 的截图回复不是 Provider 中断，也不是 LivingMemory 或表情插件把正文改坏，而是星汐旧群聊链路把一个轻度口癖重复问题升级成严重违规；唯一一次重写仍未通过后，又错误使用了“语言模块暂时打了个结”的通用兜底。

该轮最终没有回答当前消息，属于 P1 级用户可见质量回归。它不计入 owner/private typed 观察样本；P8-08-OBS 仍为 `0/20`。

## 脱敏链路证据

1. 当前轮为群聊旧链路，结构化记录为 `reply.prepared`，`is_owner=true`、`history_source=livingmemory`、Planner 调用 1 次；没有 `typed_reply.prepared`。
2. Planner、Replyer、`search_memes` 和修复调用均得到 HTTP 200；截图时间窗内没有 Provider 错误或真实请求超时。
3. `search_memes` 返回成功，只作为 presentation 工具参与，不是正文失败来源。
4. 首稿被拒绝的精确原因是 `连续复用同一角色口癖`。脱敏检查确认首稿约 46 个转义字符，仅出现一次“高性能机器人”，没有工具协议和内部规划标签。
5. `core/dialogue_quality.py` 当前只要本轮和紧邻上一条回复都包含同一角色口癖，就立即返回 `CATCHPHRASE_REPETITION_VIOLATION`。
6. `main.py` 只把 Markdown 和气泡过多视为非严重问题，因此口癖重复被当成 severe，强制追加一次模型重写。
7. 重写后仍有 1 个违规，但现有 trace 只记录数量，不记录脱敏 reason code；代码随后落入未分类 `post_violations` 分支，使用 `reasoning_safe_fallback()`。
8. 最终两气泡与截图一致；发送成功，管线总耗时约 14.1 秒，其中 Planner 约 7.7 秒、Replyer 约 3.9 秒、守卫修复约 0.8 秒。

最近 35 分钟出现过一组更早的 TimeoutError，但时间为 `14:42:23Z`，与本轮 trace 无关。HTTP 调试字段中的 `timeout=5/30` 只是连接参数，不应误计为真实超时。

## 根因

这是两个结构性缺陷叠加：

1. **质量问题与安全问题没有分层。** 单次相邻口癖复用属于风格质量问题，却和协议泄漏、身份越权、内部推理泄漏一样触发强制重写和闭锁。
2. **重写失败的回退对象错误。** 原回复只是软质量违规且仍有当前语义；重写产生新违规后，系统丢弃原语义，改发一个声称“模块故障”的无关状态文案。

同时存在一个观测缺口：`guard.post_repair_rejected` 只记录 `guard_hit_count`，无法从生产脱敏日志判断第二次究竟命中了语言、元话术、篇幅还是其他规则。

## 最小修复入口

在改码前先增加稳定回归：上一条和本轮各自然出现一次“高性能机器人”，首稿语义有效；重写返回另一种不合格文本。验收要求如下：

- 不得把一次相邻角色口癖复用直接升级成 hard failure。
- hard safety 仅覆盖协议/推理泄漏、身份/关系越权、事实边界等必须闭锁的问题。
- soft quality 重写失败时，应保留经过安全校验的原语义，不得改发虚假的“语言模块故障”消息。
- trace 只记录稳定 reason code 和阶段，不记录正文、真实用户 ID 或完整 Prompt。
- 继续保留对真正连续高频口癖和整句复读的抑制，但阈值需要跨多轮统计，不能只看紧邻一条。
