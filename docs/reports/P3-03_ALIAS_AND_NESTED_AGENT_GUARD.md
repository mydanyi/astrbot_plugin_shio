# P3-03 别名与嵌套能力防逃逸报告

## 结论

P3-03 已完成。普通群友的 v2 shadow 策略不再仅相信工具名称；同名来源冲突、间接工具分发器、插件/Agent 包装器和副作用声明冲突均失败关闭。

## 根因与风险

精确名称白名单仍有三个结构性缺口：

1. 不同插件可以注册相同或相似的安全名称。
2. 一个看似查询工具的包装器可以接收 `tool_name + arguments`，再间接调用 Shell、文件、设备或完整 Agent。
3. 工具可能声明 `public_web_read`，但同时声明或暴露 `state_write` 等更高副作用。

上述情况不能靠“问题难不难”或名称里有没有 `search` 判断。

## 实现

- 增加审计名称与实现来源的联合证明。AnySearch、LivingMemory、Meme Manager 等已审计插件名称必须来自对应模块；AstrBot 内置名称必须来自内置来源。
- 动态工具的保守语义分类只用于盘点，不自动构成授权证明；新工具要么进入审计目录，要么提供显式能力声明及可验证模块来源，并仍需管理员精确配置名称。
- 增加间接分发识别：描述中的 tool/plugin/agent dispatch、delegate、proxy、bridge 等语义，`tool_name + arguments` 一类通用参数结构，以及 alias/delegation 元数据，统一按 `agent_full` 失败关闭。
- 增加能力与副作用一致性校验。公共网页读取必须是 `public_read`；聊天检索和本地表达必须是 `scoped_read`；冲突时拒绝。
- shadow 新增未受信来源拒绝计数，不保存工具参数、用户内容或身份值。

## 回归覆盖

- 审计安全名称来自错误模块时拒绝。
- 工具分发器、别名元数据和嵌套插件代理归为完整 Agent。
- `public_web_read + state_write` 声明冲突时拒绝。
- 显式声明、可验证来源、低副作用和管理员精确配置全部满足时允许。
- 高风险语义继续优先于安全名称和安全声明。
- 管线 shadow 能同时报告来源别名和嵌套分发两类 legacy-only 差异，生产 ToolSet 暂不切换。
