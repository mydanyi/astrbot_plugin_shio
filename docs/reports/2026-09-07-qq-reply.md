# 0.5.1：QQ 无回复与聊天链路修复

日期：2026-09-07。状态：代码候选和隔离 Docker 回归完成；未部署、未推送，生产验收未完成。

## 先说结论

QQ群、QQ 私聊不回复的直接原因已定位：模型其实生成了最终答案，是 Shio 在发送之前把答案删掉了。WebChat 原生流式输出和 QQ 的发送时序不同，所以只测网页没有覆盖这个错误。

修复接续 WorkBuddy 的现有实现，保留其有效的上下文纠偏方向和按标点/换行分段能力；没有再次重构整个插件，也没有修改 AstrBot 核心。

## 1. 为什么 QQ 不回，网页却能回

AstrBot 4.27.4 的非原生流式 QQ 回复顺序是：

`最终响应 Hook → Agent 结束 Hook → 结果装饰 → QQ 发送`

WorkBuddy 增加了中间草稿拦截，但原有 Agent 结束 Hook 会清除群聊点名、私聊的“最终响应观察”。后面的装饰 Hook 看到观察为空，就误以为仍是工具调用前的草稿，执行 `clear_result()`。因此日志能显示模型成功完成，QQ 仍没有消息。

修复包括：

- 最终观察保留到 after-send，不在 Agent 刚结束时清除。
- 拦截草稿必须同时有正在运行的 Agent、同一个 ProviderRequest、尚无最终响应等证据；不能只凭“观察为空”。
- 草稿只清理本次结果，不终止整个工具循环。

修复前 Docker 红测：群聊和私聊均有 1 次成功模型请求、2 条保存的 conversation 记录，但实际发送气泡为 0。

修复后：两条链都实际发出预期文字；同一群连续多轮也能继续回复。

## 2. 为什么合并了消息还会多请求

旧代码只给批次最后真正发起请求的事件设置官方 `should_call_llm(True)`。被合并后退出的旧 @/私聊事件没有这个标记，ProcessStage 会在 Shio 退出之后为它再启动默认 Agent。

现在进入文本批次时就设置该标记，让整个批次只由最后的真实事件继续一次请求。群聊可合并不同发送者；私聊保留同一对端之前的消息。

Docker 中已验证：同群两人的两条连续消息、同一私聊的两条消息，均合入一次模型请求，并包含两条原始输入。

## 3. 为什么带表情包时又变成一整段

当前生产安装的是 Meme Manager 5.0.0。它的 `_normalize_outgoing_message_components()` 会合并相邻 Plain 文本。Shio 若在它之前分段，刚分出的 3 段会被它重新拼成 1 段。

现在顺序是：先拦确知的草稿/错误 → Meme 识别并清理标记 → Shio 对清理后的文字布局 → AstrBot 标准首发 → Shio 后续文字 → Meme 单独发图。

组合红测曾收到一个整段；修复后收到 3 个文本气泡、最后 1 张图片，工具前草稿不发送。未解析的 `&&meme:...&&` 测试标记也不会泄漏到正文。

表情包测试关闭情感辅助，确认“不启用情感辅助也可以发图”。但测试使用类别选图，不把这个结果冒充生产语义检索服务已验证。

## 4. 复读和旧会话怎么处理

已停止新增上下文污染：

- 不再查询持久化群历史作为每轮输入，不覆盖 `ProviderRequest.contexts`。
- 开启官方群聊注入时，将官方 TextPart 用 `mark_as_temp()` 标记；关闭时只补当前真实连续批次的更早消息，同样标记临时。
- 使用 AstrBot 自身的保存逻辑排除临时内容，不另写序列化系统。

Docker 红测中，官方 ICL 文本确实曾进入保存后的 conversation；修复后模型仍能看到该文本，但保存结果不再包含它。

还移除了 WorkBuddy 重载时按字符串清理 conversation 的行为。红测里，普通用户仅仅说“请解释 official_platform_history 这个术语”，消息就被重载清掉；修复后原样保留。

这不等于自动治好了所有已有污染会话。生产数据库没有被清理；模型自身是否重复、旧 conversation 是否仍有污染，需要对具体会话另行确认。

## 5. 实际验证结果

验证在独立 Docker 容器执行，使用 AstrBot 4.27.4 真实源码和当前 Meme Manager 5.0.0。

| 验证 | 结果 |
| --- | --- |
| 不加载 Meme 的回复链 | 15 个场景通过，退出码 0 |
| 加载 Meme 5.0.0 的回复链 | 16 个场景通过，退出码 0 |
| QQ @、私聊、工具调用、流式设置、工具中间消息缓冲 | 只发送预期最终正文 |
| 群聊跨发送者合并、私聊合并 | 每批次仅 1 次模型请求 |
| 普通群友/Master 未点名发言 | 都进入自然参与判断 |
| 自然参与冷却、冷却期间明确 @ | 前者安静，后者正常回复 |
| 官方群聊注入 | 模型可见，conversation 不保存该临时部分 |
| WebChat 原生流式 | 保持正常回复 |
| 插件重载 | 不删除已有 conversation |
| 当前单元回归子集 | 282 passed，2 skipped，2 deselected；244 subtests passed |

旧全量测试曾失败，其中有依赖已不存在的 Windows 临时压缩包、旧候选和旧 Hook 顺序的测试。本次更新与改动相关的断言；缺少外部材料的五个旧回放文件和两个测试明确排除，**不宣称全量绿测**。排除清单在测试说明中。

测试入口：[qq_delivery.py](../../tests/integration/qq_delivery.py)；复跑方法和边界：[测试说明](../../tests/integration/README.md)。

这不是只检查 WebUI 200，也不是重新仿写一套 Pipeline：执行的是官方插件加载器、QQ 解析、WakingCheck/Process/ResultDecorate/Respond、Provider、ToolLoop、Hooks、conversation 保存与适配器发送。配置/模型选择使用夹具；外部 OpenAI HTTP/SSE 输出和 OneBot WebSocket 对端使用合成数据。

未覆盖真实 NapCat/QQ 网络送达、所有 Pipeline 前置阶段、生产模型内容质量、真实媒体 URL 下载及生产语义检索服务。不能把隔离回归替代你的实际 QQ 验收。
