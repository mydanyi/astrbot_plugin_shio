# Shio 坑位台账

本文件记录已经真实踩过、或因审查缺口反复出现的失败模式。它不是发布宣传；每一项都规定以后必须取得的证据。示例只用脱敏／合成数据。

| ID | 已踩过的坑 | 错误假设 | 以后必须做的审查 |
| --- | --- | --- | --- |
| P-001 | 工具／推理协议泄漏不断换形：Python 样式、JSON、XML、裸参数、hidden channel | 修掉一种字符串格式就等于堵住协议 | 使用协议解析与 final-bytes guard；维护正例、反例和变体矩阵 |
| P-002 | 群聊历史存在，但普通回复、自然参与或主动发起没有走同一注入路径 | 一个聊天流程读到历史，其他流程也会自动读到 | 分流程检查 context 来源、条数、时间、scope 和真实 prompt |
| P-003 | 新消息一到就取消旧生成，连本应无动作的旁观消息也会吞回复 | “有新消息”总等价于“旧回复已过时” | 对 REPLY/WAIT/NO_ACTION 分别做并发实测和发送回执检查 |
| P-004 | 自然参与和冷场主动发起被混成一个开关、概率或冷却 | 两者都叫“主动”所以共享状态合理 | 维护两套独立状态机、开关、白名单、上下文和验收用例 |
| P-005 | 称名检测另开模型链，绕开 AstrBot 正常上下文与插件 | 检测到名字后直接生成最简单 | 只提升为正常事件；验证官方唤醒标志、上下文和插件链 |
| P-006 | WebUI 有字段但运行没读，或代码硬编码了网页没有的概率／fallback | schema 出现字段就代表功能一一对应 | schema、保存 JSON、默认、迁移、运行读取与文档做闭集对账 |
| P-007 | 主动调度被活跃时段、观察期、冷场、冷却、日限额、普通回复刷新等组合挡住 | 单看总开关即可判断为何没触发 | 日志输出每个 gate 的闭集原因；用加速配置做真实时钟验收 |
| P-008 | Meme 类别曾全部落到 happy，概率归属也在 Shio/Meme Manager 间重复 | 有图发出就算语义正确 | 以 current-turn Affect/关系选 canonical 类别；概率只归 Meme Manager；22 类正反例 |
| P-009 | 初稿被拦后 repair provider 抛异常，被改成空字符串，最终只见 empty reply | repair 失败后 fail-closed 沉默最安全 | 区分异常、reasoning-only、空 completion、解析失败、校验失败；直接问答给诚实受检 fallback |
| P-010 | 相似问题只改数字或否定对象，重复守卫误拦正确答案、语义守卫又放过旧答案改写 | 输出相似度可以代替当前问题语义 | 绑定算式、数字、比较关系和否定对象；把旧答案与它对应的旧问题成对比较 |
| P-011 | Provider 面板有 token，不代表插件拿到了可见 completion | 产生／计费 token 就一定有可发送正文 | 记录 response object、visible/reasoning 长度和 usage；不得用主模型统计冒充 repair 统计 |
| P-012 | AstrBot 知识库已配置，但最终模型看不到工具或检索事实没有密封进入回答 | 正常聊天能回答就证明 KB 已接入 | 验证 exact 内置工具来源、sealed evidence、空结果、最终事实一致性和真实 KB 问题 |
| P-013 | 普通文本正常的 provider 在 Planner JSON 上失败 | 会聊天就会稳定输出机器可读结构 | 结构化任务单独用 JSON mode、低温、token 上限和 fallback 测试 |
| P-014 | 权限判断 owner=false，但 Planner/Persona 仍把普通群友称作主人 | 权限对象正确就保证措辞正确 | 从真实 prompt/history 到 final bytes 验证身份称呼和关系边界 |
| P-015 | Persona 为了拟人编造“昨天做过／见过／经历过” | 第一人称细节只是风格 | 第一人称经历必须由角色事实或可信证据支持；无证据反例必测 |
| P-016 | 任何非空 reaction 都被当暧昧／挑逗，固定“变态”回复压过当前情境 | 情绪有值就可升级关系 | 分类触发矩阵；中性、冲突、引用、非主人分别做负例 |
| P-017 | 带图初稿进入不支持视觉的 repair provider，仍携带图片 URL | fallback provider 与主 provider 能力相同 | repair transport 绑定媒体合同并审计 provider 能力；不可见时诚实降级 |
| P-018 | “总结一下”等普通话被正则当成内部推理泄漏 | 命中内部词就是协议 | 安全正则必须有自然语言负例与协议变体正例 |
| P-019 | LivingMemory/embedding 用字符数估 token、重复图载荷、CPU/GPU 队列卡死 | 单次小样本成功可代表批量导入 | 长文本 token 边界、队列/runner/硬件、doc/chunk 计数和超时恢复分别验证 |
| P-020 | 本地、压缩包、生产目录、容器加载版本和 GitHub release 漂移 | 文件名或 metadata 一致就代表同一产物 | 每层记录版本与哈希；备份后部署；从容器内再算哈希并看加载日志 |
| P-021 | 测试／日志曾混入真实群号、QQ、聊天正文或 Provider 信息 | 测试文件不公开所以无所谓 | 发布前隐私扫描；只用 synthetic IDs 和摘要／计数 |
| P-022 | PowerShell→SSH 多层引号失败，命令实际没有在远端执行 | 本地无报错或命令看起来正确就是已执行 | 拆分命令与 SCP；检查远端返回、文件哈希和退出码；失败时明确“未变更远端” |
| P-023 | 把其他插件、后台任务或全局 provider 错误归因给 Shio | 同一时间段的 error 都是当前缺陷 | 日志按 component、trace、provider、plugin 与事件时间线归属 |
| P-024 | 单测、HTTP 200、容器 healthy、插件 loaded 后就让用户验收 | 基础设施健康等于机器人能回复 | 必须保留真实入站→上下文→模型→guard→final send→receipt 证据 |
| P-025 | 自己写代码又按同一假设写测试，自审出现确认偏差 | 测试多就自然独立 | 先写竞争假设；同时测误拦/误放；过测后重新审 diff 与未覆盖分支 |
| P-026 | 文案承诺“会重说／会重试”，但没有持久队列或真实 replay | 友好提示可以承诺未来动作 | 没有 durable enqueue/receipt 就只能诚实要求用户重发，不承诺自动重试 |
| P-027 | 把 AstrBot 全局 fallback、Meme Manager 概率或 KB 配置误做成 Shio 的第二份设置 | 为了方便调试复制设置没有副作用 | 明确配置所有权；Shio 只暴露自己拥有的 gate，不镜像外部插件状态 |
| P-028 | 隔离候选代码正确，但测试夹具先后漏带 README、CHANGELOG、AGENTS、HANDOFF 或 README 链接到的 LICENSE，完整套件被文档缺文件打断 | 复制 tests 目录就等于复制了完整验收环境；只列测试直接打开的文件即可 | harness 清单同时覆盖测试直接读取文件和公开文档的本地链接目标；候选目录从零装配后运行全部测试，任何缺件都必须补齐并从头复跑 |
| P-029 | 找到审查方法错误后，只补新用例，却继续把受同一错误假设影响的旧“通过”当证据 | 以前通过的测试与本次缺陷无关，无需重审 | 将受影响审查结论作废；全量重跑并逐项分类实现缺陷、旧夹具过期和环境装配问题 |
| P-030 | 旧自然参与测试没有显式开关、群白名单或已有上下文；为追求绿灯容易误删生产安全门 | 老测试的默认前提永远代表当前产品合同 | 保留生产 gate；给测试补真实前置状态，并同时验证 gate 关闭、上下文不足和白名单外负例 |
| P-031 | 无正文 trace 证明三轮均发送成功后，直接宣称答案语义也正确；或把 LivingMemory reader 降级误判成群历史未注入 | send receipt／日志健康等于内容正确；所有“记忆”来源是同一路径 | 发送层与语义层分开验收；语义由用户可见确认；分别核对 `group_history.read` 与 optional memory recall 状态 |
| P-032 | 自然参与和冷场续题触发状态机虽已独立，却各自复制 Provider／发送旁路，导致规则、完整 Persona、检索、气泡或 Meme 在其中一路缺失 | “触发独立”就等于整条链都应该独立；各模块单测通过即可证明集成 | 独立触发、共享下游合同；同一 canonical request 联合断言可信上下文、按需 sealed read、完整 Persona、segments、逐段回执与共享 Meme Manager transport |
| P-033 | 部署脚本把通用 `EXIT` trap 直接等同于回滚，预检阶段失败也可能停止并重启尚未进入切换的健康容器 | 有回滚 trap 就一定比没有安全；预检失败也该“恢复”服务 | 以 `CUTOVER_STARTED` 和各资源移动状态分层；切换前失败不得碰容器或 live；切换后失败才按插件／配置各自状态恢复。P10-18 的 `deploy/deploy_v0518.sh` 固化此边界 |
| P-034 | 启动日志粗略搜索 `error`，把 `contract_error_count=0` 这类健康指标键误报为启动错误 | 任何包含 error 的行都等于 ERROR 事件 | 先按真实日志级别、Traceback 和失败 component 计数，再检查 `*_error_count` 是否非零；不得用字段名命中冒充异常 |
| P-035 | 主动场景测试预先喂入带换行的两段模型输出和明确 `food` 话题，证明了两气泡／Meme 能力可达，却没有暴露真实弱模型长期只给单段、真实话题很少命中类别的问题 | 一条同请求联合正例同时覆盖多个模块，就足以证明真实使用频率与效果 | 将“能力可达”与“真实分布”分开；除联合正例外，必须用当前生产 provider、真实脱敏话题分布和连续多轮统计气泡率、Meme eligible 率、Manager 条件成功率，并设置可验收阈值 |
| P-036 | Meme Manager 已设 100%，但 Shio 仍有独立概率／冷却／长度门，或在最终回复前把普通聊天截断 | 下游概率归 Manager，就等于整体图片率也由 Manager 控制 | Shio 不保留第二套概率／冷却；普通／自然由 Manager 正常钩子决定，主动／冷场只有硬安全与“存在可解释类别”门。分别记录路径、Manager probability 和最终图片回执 |
| P-037 | Meme Manager 图片已完成 caption、embedding 和索引，但请求来源范围或钩子顺序错误会让逐图语义库零调用；公开类别兼容接口能发图也不能证明逐图检索工作 | 索引 ready、图库完整且兼容接口能发图，就代表实际回复使用了语义选图 | 普通／自然按真实请求记录 origin、semantic mode、候选数、selected ID 与回执；主动／冷场明确记为类别兼容路径，不冒充 caption/tags/vector 选择 |
| P-038 | WebUI 的 Shio `replyer_provider_id` 看起来像“回复模型”，但普通入站首稿实际沿用 AstrBot 默认 provider；该字段只被主动生成与 repair 显式读取 | 一个名为回复模型的字段自然控制全部回复；看到某模型配置就可把所有输出归因给它 | 对普通首稿、自然参与、冷场主动、repair、视觉和 embedding 分别记录实际 provider ID/digest 与配置所有者；质量 A/B 必须命中出问题阶段的真实模型，不能按字段名猜路由 |
| P-039 | Shio 已读到 16 条群历史，却清空原生 message contexts，把当前问题、历史、Persona、情绪和合同序列化进一个大 user prompt；量化模型直问会答，经过该重打包却漂移 | 只要 prompt 里能搜索到历史文本，就等价于模型以清晰对话角色和顺序接收了上下文；弱模型答坏即可归因模型 | 同一真实模型做三段式 A/B：原问题裸问、加最小可信 message context、完整插件请求；比较对象、动作、指代、否定、直接回答和事实边界。上下文“存在”与“可用”必须分开验收 |
| P-040 | 当前 validator 能拦旧答案串题和关系对象漂移，却会放过复述当前问题、把能力问题说成“新指令”、凭空换成联发科等非答案 | 出现当前关键词／没有复制旧上下文就代表围绕问题作答；Persona 自然即可弥补内容缺失 | 为直接问答增加可反驳的 answer predicate：问题复述、无关新实体、能力事实缺失、事实边界被角色幻想替换均为反例；每项同时保留自然简答正例。不得只用实现自产的 anchor/关键词判据验收语义 |
| P-041 | 日志或提示词能搜到历史正文，但 Provider 收到的是一个大型 user JSON，而不是按真实角色顺序排列的原生 messages | “文本存在”就等于上下文可用；弱模型会自行恢复说话人和时序 | 对真实 Provider 请求断言 `contexts` 的 role、顺序、来源、边界和当前消息排除；同一句问题保留裸问／最小原生上下文／完整插件三段式 A/B |
| P-042 | WebUI 配置过知识库、联网或 Agent，Persona 就声称本轮拥有；实际工具可能已被权限门移除或根本未接入 | 配置能力等于本轮有效能力 | 能力快照只能由权限过滤后的 exact tool inventory 与 typed policy 生成；能力问答测试必须同时覆盖可用、不可用和禁止虚构正向接入 |
