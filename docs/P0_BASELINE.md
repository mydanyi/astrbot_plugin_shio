## 2. 当前稳态阻塞调用数

以下计数来自当前代码路径和实际启用配置。AstrBot 主 Replyer 调用计入；本地字符串处理和数据库读取不计入 Provider 调用。

| 场景 | 当前稳态阻塞步骤 | 最低 Provider 调用数 | 额外情况 |
| --- | --- | --- | --- |
| 普通直接聊天 | Planner LLM -> 查询 Embedding -> Reranker -> AstrBot Replyer LLM | **4** | 表达文档向量缓存首次未命中时，再增加 1 次批量 Embedding |
| 复杂群聊但不联网 | 与普通直接聊天相同 | **4** | Planner 主模型失败时，备用 Planner 再增加 1 次 |
| 普通群友联网聊天 | Planner -> Embedding -> Reranker -> Replyer 工具决策 -> 工具 -> Replyer 最终回答 | **至少 5 次 Provider/模型循环** | AstrBot 工具循环、Provider 重试或多次搜索会继续增加 |
| 回复触发严重输出违规 | 正常链路 + 无工具修复 Replyer | **普通聊天至少 5** | 修复失败还会进入安全降级或恢复队列 |
| 主人显式 `/agent` 或 `/task` | 星汐在规划前交还 AstrBot | **星汐额外 0** | 实际调用由 AstrBot Agent 任务决定 |

代码依据：

- `main.py` 在每次角色聊天中调用 Planner。
- `style_retriever.py` 在配置 Embedding 时每轮调用查询向量；文档向量只在缓存命中时免除批量请求。
- 候选数大于 `top_k` 且配置 Reranker 时，每轮执行精排。
- 星汐完成请求改写后，AstrBot 再执行真正的 Replyer LLM。
- 输出守卫命中严重违规时，可能调用独立修复 Provider。

## 3. 当前延迟测量边界

旧链路没有贯穿输入、Planner、上下文、Replyer、守卫和最终气泡的统一 trace：

- Planner 只明确记录失败、超时和备用接管耗时，不记录每次主 Provider 成功耗时。
- AstrBot 主 Replyer 与星汐内部 Planner 没有共用的脱敏 request ID。
- 最终气泡发送前后的时间没有与同一目标消息关联。
- 因此，现有历史日志不能可靠计算简单聊天、复杂群聊和联网聊天的端到端 p50/p95；用日志行相邻时间推测会重现本项目正在修复的“按时间相邻错误归因”。

本阶段拒绝填写虚假的绝对延迟数字。

## 4. 新增的后续测量能力

P0-03 已增加事件级、无正文的 pipeline trace，阶段为：

1. `input`
2. `context`
3. `plan`
4. `raw_reply`
5. `final_reply`

每个阶段保存相对 `elapsed_ms`、字符/消息计数、不可逆内容指纹和结构状态，不保存正文或原始身份。当前 trace 同时明确暴露：

- `memory_subject_model=untyped`
- `has_target_message_id=false`
- `target_model=text_only`
- 原始回复与最终回复是否发生改变

目前 trace 只在本地实现，尚未部署生产。P8 影子部署后，至少收集以下脱敏样本再形成真实延迟基线：

| 样本类型 | 最低样本数 | 记录字段 |
| --- | --- | --- |
| 普通直接聊天 | 30 | 阶段耗时、调用数、是否重写、气泡数 |
| 多用户/复杂群聊 | 20 | 阶段耗时、目标是否变化、调用数 |
| 联网聊天 | 20 | 阶段耗时、工具轮次、调用数 |

只有在 v1 和 v2 都有同口径数据后，才比较 p50/p95。目标仍是：普通聊天降为一次阻塞 LLM 调用，复杂/歧义场景最多两次，表达和学习不再额外阻塞热路径。
